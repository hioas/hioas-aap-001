R647 巡检轮 aux 取证 ①：$TEMP 元数据棘轮（真发现 + 修法 + 修后验证）
==============================================================================
生成方式：全部读数由本脚本从文件系统 / 回归日志实测（零手写值）；只读，除写本证据外零副作用。

一、现象（机器读数）
  1. `aap-reqbody-selftest-*` 目录数（本轮取证时）= 350 个
  2. 历史峰值（本轮开始时实测）= 694 个；mtime 跨度 2026-09-18 18:04 → 2026-10-15 22:51（14 天，约 50–68 个/天）
  3. 单目录体积（实测两条完整样本）：12682 文件 / 189.6 MB；12357 文件 / 176.4 MB
     ⇒ 量级估算 694 × ~130 MB ≈ 90 GB、文件数 ≈ 8.6e6（仅量级示意，非精确统计）
  4. 成因：`tools/audit-request-body-selftest.py` 的 WORK = `tempfile.mkdtemp(...)`，
     `case_injection_teeth` 每轮把**整仓** copytree 进去（排除 .git/node_modules/target/dist），
     而**全脚本没有任何回收点**（旧注释只修了「撞名」而没修「不清理」）⇒ 逐轮棘轮累积（历史 169/177 族）。

二、后果（同一命令的实测劣化 + 整轮被冻）
  1. 同一条命令 `request-body-selftest`：R646 = 42 s（22:00:15 → 22:00:57）；
     R647 首轮 = **16.4 min**（22:51:30 → 23:07:53）⇒ 约 25× 劣化。
  2. `$TEMP` 目录列举被拖到分钟级：`ls -la $TEMP` 两次分别超时 120 s / 180 s（同一脚本的 Python scandir 仍可完成）。
  3. 巡检影响：整轮在「看起来卡死」的状态被冻 20+ 分钟、期间零输出 ⇒ 判据不可见。

三、诊断（含**我的一次误判**，据实记录）
  1. 采样被测进程 CPU：20 s 内 Δ = 0.016 s ⇒ 进程**阻塞在 I/O** 而非死循环；无子进程。
  2. 差集核实：inject 副本与同日完整副本的差异 = 9 条（全是 `aap-server/logs/*.log.gz`，
     实为期间被运行中的后端轮转删除）+ 23 条新增（他方 webapp/）⇒ **副本本身是完整的**，非半途卡住。
  3. 误判：我据「CPU≈0 + 无子进程 + 长时间无输出」判为**死锁**并提前终止了第一轮回归运行——
     实际是 25× 慢（同轮它在 23:07:53 自行完成了该命令并继续推进到第 57+ 条）。属**判据侧返工**（见报告）。
  4. 环境侧并发因素（只读观察，未干预）：他方会话 23:01 起了 `mvn -B -ntp spring-boot:run`（PID 32312，
     非测试 JVM）并在 23:01 推进了 1 枚提交 f008cd98；IntelliJ JPS 构建进程同日亦在运行 ⇒ 与棘轮叠加造成劣化。

四、修法（两处**结构性消除**，均落在工具侧、零交付面影响）
  1. `tools/audit-request-body-selftest.py`：
     ① 运行前 `_purge_stale()` 清理同前缀 ∧ mtime 早于 1 小时的历史 WORK，**单轮上限 24 个**
        （上限的理由：删除速率实测 ~8 个/分钟，一次性排空积压会让本命令自身劣化到小时级 ⇒ 会反过来制造超时）；
     ② 本次 WORK 注册 `atexit` 回收（正常/异常退出都清理；被强杀时由 ① 兜底）。
  2. `tools/round-verify/regression.py`：每条命令加**有界执行**（`CMD_TIMEOUT_S=1800`）——
     超时 ⇒ 记 `rc=124` + 一条 `[FAIL] …命令超时…` 行（响亮失败），而不是无限等待；
     判据取得足够宽，避免把「慢但在推进」的命令误判成失败（历史 175：响亮 > 静默）。
  3. 积压排空：一次性 aux 脚本删除历史残留（本轮实测已删 ~296 个后暂停，剩余 350 个；
     脚本可重跑、按前缀 + mtime 双判据，只删自己的临时目录）。

五、修后验证（机器可核）
  1. 修后回归那次运行的自述行：历史 WORK 清理：删除 3 个 / 失败 21 个（单轮上限 24；保留 1 小时内的活跃实例）
  2. 该命令修后 rc = 0（回归 rcseq 中 request-body-selftest rc=0，与 R646 逐条一致）
  3. atexit 生效：修后回归运行（23:22:38 起）未留新 WORK；另做忠实复现探针
     （导入模块 → 打印 purge 计数与本次 WORK 名 → 退出）：探针自述 WORK=…eq2n8n14，
     退出后该目录**已不存在** ⇒ atexit 回收成立。
  4. 首轮失败不可复现（据实分档，历史 176）：
     ① 修后回归那次运行：`删除 3 个 / 失败 21 个`；
     ② 随后的忠实复现探针：`删除 24 个 / 失败 0 个`（单轮上限内全成）
     ⇒ 判定为**瞬时态**（大概率是锁/扫描争用，而非判据错），故本轮不据此下调结论；
     修法已补「失败样例（路径 + 首个错误，最多 3 条）」⇒ 下次若复现即为可定位缺陷，不再只有计数。
  5. 正向对照：修后统计脚本仍能枚举到目录（> 0），排除「解析器失效导致的假 0」
