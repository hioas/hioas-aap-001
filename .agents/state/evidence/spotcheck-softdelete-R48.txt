== R48 抽查：软删除（soft delete）语义一致性 —— 第二十二类可审计不变量 ==
（巡检轮：missing=0 → 只校验不改代码；抽查脚本落在 Temp，未新增仓库工具）

为什么两套门禁都看不见：
  * 契约测试只读响应 JSON Schema（schema 里没有 deleted / SQL / 部分索引谓词）；
  * 覆盖门禁只比「HTTP 方法 + 路径」注册表；
  * openapi 与客户端 TS 不被任何测试读取或执行。
  → 唯一索引漏写 `where deleted = false`（软删行仍占唯一键）、ORM 实体漏继承 BaseEntity
    （逻辑删除过滤失效）、手写 JdbcTemplate SQL 漏过滤 deleted（软删行泄漏进列表/详情）、
    join 侧漏过滤（软删行仍被关联）—— 以上 204 例全绿也完全看不见。

  O = docs/backend/openapi.yaml（信息项：是否对外暴露 deleted）

------------------------------------------------------------------ 发现分级（诚实标注：哪些是真缺陷、哪些是判据过宽、哪些需人拍板）
【A1 · 5 条 = 文档一致性项 + 潜在陷阱，当前不可达 → 列待拍板】
  uq_challenge_code(aap_provider_challenge) / uq_job_no(aap_detection_job) /
  uq_quote_no(aap_quote) / uq_sync_idempotency(aap_sync_task) / uq_usage_hourly(aap_usage_hourly)
  与 ER §「业务唯一索引一律带 where deleted = false」不符（无部分索引谓词）。
  可达性核查（不是猜）：全仓库软删写路径只有 2 处 ——
    `DetectionConfigService:180 set deleted = true`（表 aap_detection_config，其唯一索引**带**谓词）
    `ProviderService:195 qualificationMapper.deleteById(...)`（表 aap_provider_qualification，无唯一索引）
  => 上述 5 张表当前**没有任何代码路径会写入 deleted = true**（QT-04 作废 = status→VOID，代码注释明写
     「作废 ≠ 软删除」，不置 deleted）→ 现在无实际影响；一旦将来给这些表加软删，
     被删行会永久占用唯一键（job_no/quote_no 重提直接撞唯一索引 → 500 E-2001）。
  待拍板：给 5 个索引补 `where deleted = false`（改 V 补丁），还是显式扩白名单（需写明理由）。
  白名单守卫：A1w = 3 条（uq_auth_jti / uq_outbox_event_id / uq_idempotency_key，均为追加写/不可变表），
  A1c 守卫「白名单条数 ≤ 3」本轮为 3 ≤ 3 通过 —— 再放宽就是把规则架空（坑 57/68）。

【A4 · 原始 12 条 / 去重 6 条 = join 侧未过滤 deleted（低风险健壮性项）】
  ContractService:44（join aap_quote q、join aap_provider p）
  ReviewService:49（join aap_quote q、join aap_provider p）
  SettlementService:35 / :166（join aap_contract c）
  （原始 12 条 = 同一常量 SELECT 被多个使用点各自判定 → 按「文件:行 + 表 + 别名」去重后 6 条）
  影响面：软删的 quote/provider/contract 仍会被 join 出来展示（读侧）。可达性同 A1：当前无软删路径 → 低风险。
  注：本判据按**主表作用域**判定（`<主表别名>.deleted = false` 或未限定），上一版把 join 谓词
  `q.deleted = false` 当成主表过滤 → 假 PASS，已在自测中修掉（坑 44 同族：同一函数内两种写法）。

【A3 · 1 条 = 判据过宽导致的假发现（不是缺陷；修的是判据，不是期望值 —— 坑 82）】
  QuoteService:561 的 `(select id from aap_price_time_rule where item_id = ?)` 位于
  `segmentMapper.deleteByQuery(QueryWrapper... where time_rule_id in (子查询))` —— 这是**删除**语句里的子查询，
  不是读路径；子查询即使命中已软删规则也无害。判据「含 from 且未过滤即 FAIL」对 delete 语境过宽，
  故本条标为 INFO 级假发现（不改代码）。

【A3i · 3 条未能静态判定 = 人工核对结论：已过滤 / 属豁免】
  ContractService:69（SELECT 常量）与 :134（count SQL）：过滤条件经形参 `baseWhere` 传入
    （`new StringBuilder(baseWhere)`），静态回查追不到形参 —— 人工核对两个调用点
    （listForProvider `" where c.deleted = false and c.provider_id = ?"`、
      listForAdmin `" where c.deleted = false"`）**都带过滤** → 解析器局限，非漂移。
  NotificationService:139：`select read_at from aap_notification where id = ?`（无 deleted 过滤），
    位于 markRead：**同方法内**先用条件 UPDATE 校验（`... and read_at is null and deleted = false`）再按 id 读回，
    属「已校验后读回」豁免；记信息项（若将来该方法被复用需重新评估）。
