-- 结论（据实分级）--
① **真漂移（契约一致性项，交付物侧）**：成功响应**实际输出 5 个键**（code,message,data,traceId,details），而 md §0 / `envelope.schema.json` / openapi `Envelope` 组件 / 客户端 `ApiEnvelope` 接口**四处一致地只声明 4 个键**（code,message,data,traceId）—— 差异键 = `details`（成功路径恒为 `null`）。四处同侧 ⇒ 判**实现侧为漂移侧**（历史 51：用多方裁判定案）。该漂移**对两套门禁完全不可见**：`envelope.schema.json` 的 `additionalProperties = true` 放行额外键 （契约测试仍绿），覆盖门禁只比「方法 + 路径」，openapi 与客户端 TS 不被任何测试读取/执行；且**键集合断言 = 0 处**（成功路径额外键零用例背书）。运行风险低（客户端忽略未声明键），但违反「字段集合」契约，且与「缺字段一律 null / 禁止 0 冒充没有数据」的既有约定的**语义方向相反**（多出一个无语义空字段）。修法面二选一（须人拍板）：① 生成器给成功 schema（+ openapi 组件）补 `details` 声明（改生成物）；② 让成功路径不输出 `details`（改序列化策略或 `ok()` 侧注解 —— 会触碰既有约定与既有用例）。
② **信息项（同族已在册）**：openapi 的 `in: header` 声明数 = 0 ⇒ 响应头 `X-Trace-Id`（md §0 明写语义）在 openapi 零声明；与在册「幂等头 openapi 零声明」同族。
③ **信息项（客户端侧）**：`ApiError` 声明 `details` 而构造点 5 处**无一**从包体取值（恒传 undefined）⇒ 死字段；客户端也不设置请求头 `X-Trace-Id`（0 处）⇒ 实现承诺的「客户端已带则沿用（跨服务链路不截断）」在客户端侧无人履行。
④ **正面结论（机器取证）**：traceId 出口四面一致 —— 头名 `X-Trace-Id`（md == `TraceIdFilter.HEADER`）、MDC 键 == 包体字段名 == `ApiEnvelope.TRACE_ID` == `traceId`、客户端确实从包体读取 traceId（['code', 'data', 'message', 'traceId']）；失败路径 schema 与实现出口**逐键相等**（True）⇒ 漂移**只在成功路径**、非全局。
