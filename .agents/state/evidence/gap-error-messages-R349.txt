-- 真发现（机器取证）--
① **「错误码对外文案（message）」这一轴在契约与客户端两侧**同时无约束**（结构性缺口）**：契约侧 `error.schema.json` 对 `message` 只约束 `minLength: 1`（**无 enum / 无 pattern**）；客户端 `http.ts` **直接透传**服务端 `message`（透传点 3 处、**按码映射 = 0 处**）⇒ 用户看到的那句话**完全由服务端枚举文案决定**，而它零契约约束；对照组：同一份契约里 `code` 有枚举 + 契约测试守卫（`code()` 断言 178 处）⇒ **同族两轴「一守一不守」**。
   为什么两套门禁都看不见：契约测试只把**真实响应**与 schema 比 —— `message` 是自由字符串，改成任何一句都照样全绿；覆盖门禁只比「方法 + 路径」；openapi 与客户端 TS 不被任何测试读取/执行；而测试侧 `message()` **文本断言仅 3 处**（且**无一处**把实现文案与文档 §4 比对）⇒ 该轴**零自动化见证**（历史 81 的测试侧形态）。
   风险分级（诚实）：**非线上故障**（当前文案与 §4 语义一致、客户端也从未按文案分支）；属**契约完整性缺口** —— 文案可被任意改写而无门禁拦截，且**文档 §4 的『场景』列与实现文案逐码措辞不同**（4 条 md 更详细 / 20 条措辞不同），调用方若照文档写文案或做包含判断会分叉。
   修法（三选一，均属**改交付物/文档/测试面** ⇒ 按「missing==0 -> 只校验不改代码」未改，列待拍板）：① 给 `message` 加契约约束（enum 或 pattern）；② 在契约测试里补「文案 ⇔ §4」一致性断言；③ 明确声明 md §4 是**规格语义**、枚举文案是**用户文案**，二者无一致性要求（写入契约说明）。
