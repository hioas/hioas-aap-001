== R123 机制取证：`token[:-2] + "xy"` 篡改在 1/1024 的情形下不改变签名（机械复现） ==

判据（不需要任何密钥 —— HMAC-SHA256 输出均匀分布，密钥不影响分布）：
  JWS 签名 32 字节 → base64url 43 字符；字符 i 覆盖位 6i..6i+5，总有效位 256。
  字符 42（末位）覆盖位 252..257 → 位 256/257 是填充位 → **只有高 4 位参与解码**（低 2 位恒 0）。
  字符 41 覆盖位 246..251 → 6 位全部有效 → 只有原字符恰为 'x' 时才不变。
  ⇒ 篡改后解码签名不变 ⟺ 第 42 字符 == 'x' ∧ 第 43 字符 == 'w'（末位取值只能是 16 个值之一，故 'w' 的概率 1/16）
     → 概率 = (1/64) × (1/16) = **1/1024**。

实测（probe-jwt-tamper.py，样本 200000 个随机 32 字节签名）：
  样本数 = 200000（正向对照：必须 > 0）
  篡改后**文本与原 token 完全相同**（原末两字符恰为 'xy'）= 0 次（理论 1/4096 = 48.8）
  篡改后**解码签名与原签名相同**（→ 服务端验签通过 → HTTP 200）= 202 次（理论 1/1024 = 195.3）
  实测频率 = 0.10100%（理论 0.09766%）
    末字符对照：w vs y → 解码相同 = True
    末字符对照：x vs y → 解码相同 = True
    末字符对照：y vs y → 解码相同 = True
    末字符对照：z vs y → 解码相同 = True
    倒数第二字符对照：'x' vs 'A' → 解码相同 = False
  
  结论：`token[:-2] + "xy"` 在约 1/1024 的情形下**没有真正改变签名**（末位 base64 填充位不参与解码），
        服务端验签通过 → 200，而测试断言 401 → 这是**测试侧断言缺陷**（篡改不保证有效），
        与实现无关（R122 全绿；同一机制对 211 例中的其它验签用例同样成立）。

条件分布实测（probe-jwt-tamper-diag.py）：命中项**全部**是 (第42字符=='x', 第43字符=='w')，无其它形态 → 判据完整。
  样本 200000
  末字符（index 42）取值分布：{'8': 12610, 'o': 12615, 'Q': 12441, 'k': 12445, 's': 12422, 'w': 12562, 'E': 12437, 'A': 12609, '4': 12471, 'I': 12643, '0': 12394, 'M': 12299, 'g': 12514, 'Y': 12482, 'c': 12561, 'U': 12495}
  末字符值 mod 4 集合 = [0]（若恒为 0 → 末字符只有高 4 位有效）
  命中（篡改后解码签名不变）的条件分布：
     char41=='x' = True, char42 = 'w'（值 48）→ 228 次
  样例（char41, char42, 值）：[('x', 'w', 48), ('x', 'w', 48), ('x', 'w', 48)]
  合计 = 228（实测频率 0.11400%）

⇒ 结论：该 flaky 的**根因与概率都是确定的**（1/1024），与实现无关；R122 全绿、R123 run2 全绿与该机制不矛盾。
