# 报价模型设计与计费表达式编译规则

> 回答一个问题：供应商用业务语言填的报价单，如何零人工翻译地变成 new-api 可执行的计费表达式？

## 1. 报价单数据模型（供应商填写）

### 1.1 三层结构

* 报价单 Quote：基本信息（供应商、有效期、币种、备注）+ 明细行 QuoteItem\[]
* 明细行 QuoteItem：模型标识（model\_name/model\_alias）、基础单价、时段价规则、阶梯价规则、请求级加价规则

### 1.2 单价字段定义（单位 \$/1M tokens，真实单价）

| 字段                              | 必填 | 说明              |
| ------------------------------- | -- | --------------- |
| `input_price`                   | ✅  | 输入（未命中缓存部分）     |
| `output_price`                  | ✅  | 输出              |
| `cache_read_price`              | ❌  | 缓存命中读取价         |
| `cache_write_price`             | ❌  | 缓存创建价（5min TTL） |
| `cache_write_1h_price`          | ❌  | 缓存创建价（1h TTL）   |
| `image_input_price` / `audio_*` | ❌  | 图片/音频           |

> 这些是真实单价，直接对应 `billingexpr` 系数，无 ratio 转换、无 `/2` 约定。若供应商只给倍率，需"参考价 × 倍率"换算后仍存真实单价。

### 1.3 时段价规则（峰谷）

字段：`tz`、`weekday_scope`(ALL/WEEKDAY/WEEKEND)、`peak_ranges[]`（可多段，start/end）、`peak_multiplier`、`offpeak_multiplier`。区间语义 start 含 end 不含。支持跨零点（22:00–06:00 → `hour >= 22 || hour < 6`）。

### 1.4 阶梯价规则（分段）

字段：`tier_field`（固定 len）、`tiers[]`（min/max/label）、`price_strategy`（OVERRIDE=各档独立定价 | MULTIPLY=各档倍率）。半开区间 `(min, max]`。

## 2. 编译总览

报价单 JSON → \[编译器] → billingexpr 表达式 → \[校验器] 样例 token 向量模拟求值比对预期 → \[人工确认页] 展示填单原文/编译表达式/模拟账单 → 确认后才写 new-api option。
**三道闸门**：编译 → 模拟验证 → 人工确认，任一不过不落 new-api。

## 3. 编译规则（核心）

### R1 基础价

输入 `input=2.5, output=15, cache_read=0.25` → 输出 `v1: tier("base", p * 2.5 + c * 15 + cr * 0.25)`

### R2 阶梯价（★ 必须用 `len` 而非 `p`）

```
v1: len <= 512000
  ? tier("t0_0_512K", p * 2.5 + c * 15)
  : (len <= 1024000
      ? tier("t1_512K_1M", p * 5 + c * 30)
      : tier("t2_1M_plus", p * 10 + c * 60))
```

原因：`p` 会被自动排除机制扣减（缓存命中导致 `p` 变小），用 `p` 判档会误判；`len` 始终反映完整上下文长度。

### R3 峰谷价

峰值判断抽为公共子表达式 `hour("Asia/Shanghai") >= 9 && ... < 12 || ...`，峰值价 = 基准价 × peak\_multiplier，非峰值 × offpeak\_multiplier。工作日/周末用 `weekday(tz)`。

### R4 阶梯 × 峰谷（组合，最复杂）

策略：外层分档（`len`），内层分时段（`hour`），每个档位内部独立应用峰谷倍率。档位命名 `t{index}_{label}.{时段}`。

### R5 请求级加价（可选）

`|||` 语法：`v1: tier("base", p*5 + c*25)|||when(header("anthropic-beta") has "fast-mode") * 6`。本期只在管理端高级模式开放。

### R6 多模型

一个报价单 N 个模型 → N 条独立表达式，分别写入 `billing_setting.billing_expr[model_name]`，失败可单模型回滚。

## 4. 编译器实现要点

### 4.1 编译产物结构

含 `compiled[]`（model、expr\_version、expr、tier\_labels、source\_hash、verified、verify\_report）。`source_hash` 用于幂等与变更检测。

### 4.2 模拟校验（★ 强制闸门）

用样例 token 向量跑表达式，比对预期。用例：基础（prompt=1000/completion=500）、缓存命中（p=800 + cr=200 计价）、阶梯边界（len=512000 vs 512001）、时段边界（09:00/08:59/12:00/18:00 半开区间）、组合（len=600000@10:00 命中 t1.peak）。
校验失败必须定位到报价单字段。
边界冲突检测（编译前）：时段重叠、阶梯重叠/空洞、倍率 ≤0 或 NaN、单价为负 → 拒绝。

### 4.3 幂等与变更

`source_hash` 不变跳过同步；变更生成新表达式 + 保留旧快照；写入前对比线上现值，写入后回读校验。

## 5. 商业含义

* 对供应商：不用懂 new-api，报价灵活度 = 实际计费灵活度，无降级。
* 对运营：消灭"Excel 报价 → 手工配倍率"的翻译环节，定价错误率归零。
* 对账：档位标签落在日志，可精确定位实际计费构成。
* 议价：历史报价快照可追溯。
* 可扩展：新价格维度只需扩展编译规则，不动 new-api。
