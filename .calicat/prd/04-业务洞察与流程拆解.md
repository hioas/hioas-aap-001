# 业务洞察与流程拆解

## 1. 心智模型：这是一条"供应商进件流水线"

供应商 → 注册登录 → 提交测试凭证(URL/Key/模型) → 检测引擎(TTFT/P50/一致性/RPM/TPM/缓存命中/模型指纹/真实源) → 检测报告(可解释) → 短信通知 → 填写报价单(多模型/峰谷/阶梯) → 审核 → 发起合同 → 签署 → 打款 → 编译 billingexpr → 建渠道+写价格(new-api) → 定时任务拉 log 聚合用量

## 3. 核心状态机

### 3.1 供应商主状态（Provider Lifecycle）

注册成功 → 待提交凭证 → 检测中 → 检测通过 / 检测未通过（可改凭证重测）→ 报价中 → 待审核报价（可驳回）→ 待签合同 → 已签约 → 待打款 → 已上架 → 供货中 → 终止合作

### 3.2 检测任务状态

排队中 → 执行中 → 分项完成 → 全部完成 → 报告已生成；执行中 → 执行失败（重试 ≤N 次）

### 3.3 报价单状态

草稿（可多次暂存/修改）→ 已提交（可撤回）→ 审核中 → 已驳回（改后重提）/ 已通过 → 已转合同

### 3.4 渠道上架状态（new-api 侧）

待同步 → 同步中 → 已同步 / 部分失败（重试）→ 已启用 → 已停用（供应商异常）→ 恢复

## 4. 痛点分层（金字塔拆解）

* ⑤ 无法按供应商对账结算（商业层：钱算不清）
* ④ 上架靠手工（效率层：慢且易错）
* ③ 报价靠 Excel/微信（效率层：无法结构化）
* ② 无法验真（信任层：★ 最核心）
* ① 信息散落（基础层：无单一事实源）

**洞察**：市面"API 中转/聚合"痛点普遍集中在 ①③④（信息与效率），但 ②（验真）才是真正的信任缺口——供应商超卖、把 GPT-4o 换成 mini、把共享池冒充独享。谁先把"验真"做成可解释的标准动作，谁就掌握议价权。

→ 产品定位：做"供应商质量验真 + 自动计费编译"，不做"又一个接入管理后台"。

## 5. 差异化的两个技术支点

### 支点一：多维指纹交叉验证（对应痛点 ②）

| 维度           | 探测手段              | 能识别什么           | 局限             |
| ------------ | ----------------- | --------------- | -------------- |
| 自我认知         | 问"你是谁/训练截止"       | 明显模型替换          | 易被系统提示伪装       |
| Tokenizer 指纹 | 同一文本比 token 数     | 不同 tokenizer 家族 | 同家族内无法区分       |
| 行为指纹         | 特定题目对错模式          | 能力档位            | 需题库+回归基线       |
| 概率指纹         | logprobs top-k 分布 | 同模型不同量化/版本      | 需上游开放 logprobs |
| 延迟签名         | TTFT/TPS 分布       | 硬件档位、共享池        | 受网络影响          |
| 一致性          | temp=0 多次采样比对     | 是否路由到多后端        | 上游缓存会误导        |
| 真实源          | DNS/证书/响应头/错误格式   | 实际是哪家上游         | 中转可掩盖          |

→ 产品化关键：不是给"真/假"二元结论，而是给每项打分 + 证据链 + 置信度。

### 支点二：报价 → 计费表达式编译（对应痛点 ③④）

供应商业务语言（"9-12 点峰价是谷价 2 倍"、"0-512K 一档"）→ 系统编译 → new-api `billingexpr` → 自动写库。价值：供应商不需要懂 new-api，运营不需要手算倍率。
