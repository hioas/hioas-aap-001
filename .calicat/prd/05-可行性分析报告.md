# 可行性分析报告 — hioas-aap

> 结论先行：可做，且不需要改造 new-api。但有 3 项需要调整预期，1 项建议砍掉换方案。

| ----------------------------- | ------------ | ------------------------------ |

## 2. 最强可行性证据：与 new-api 的集成

**结论：AAP 是外挂系统，new-api 零代码改动。**

* **路径 A：建渠道（上架）** → `POST /api/channel/`（AddChannel，需 ChannelSensitiveWrite）。Channel 25+ 字段已覆盖供应商提交的全部信息。
* **路径 B：写价格（编译表达式）** → 写 option `billing_setting.billing_expr[model]`。`billingexpr` 原生支持峰谷价、阶梯价、缓存价，业务报价可 1:1 表达，无需降级转换。
* **路径 C：用量核算** → `SumUsedQuota(logType, start, end, model, ..., channel, group)`，已有 channel 维度，按小时切时间窗即可。

**"零改动"至关重要**：不需维护 new-api fork，不产生升级冲突；集成面是稳定的管理 API；出问题可快速降级为人工在 new-api 后台操作。

## 3. 需要调整预期的 4 项（诚实清单）

### 3.1 ⚠️ 模型指纹：是"证据链"，不是"验真证明"

做不到 100% 确定。原因：中转商可在响应层做模型映射伪装；自我认知探测可被系统提示改写；logprobs 概率指纹需上游开放；真实源若走 CDN/反代只能看到边缘节点。
**可信表述**：系统输出"模型一致性置信度"+ 证据链，而非"真/假"。
**产品应对**：多维交叉（≥3 维一致才给高置信）、披露置信度、建立基线库、定期复测、免责表述（不得写"保证为真模型"，写"未发现不一致迹象"）。

### 3.2 ⚠️ 电子合同：一期建议线下

线上签署需接第三方（e签宝/法大大/上上签），涉及资质、费用、对接工期与合规。一期走线下：模板填充 → 双方盖章 → 上传扫描件 → 记录状态。二期预留 `sign_channel = ONLINE | OFFLINE`。

### 3.3 ❌ 打款：建议不做资金流转

系统只记录打款状态 + 凭证（单号、金额、时间、截图），资金走线下对公。字段预留 `settlement_status`。

### 3.4 ⚠️ 缓存命中用量：Log 表无独立字段（F8）

| 方案        | 做法                                      | 评价                |
| --------- | --------------------------------------- | ----------------- |
| A         | 解析 Log.Other JSON 提取缓存 token            | 依赖 other 结构稳定性，耦合 |
| B         | 从 billingexpr.RunExprWithRequest 求值轨迹采集 | 需改 new-api，违背零改动  |
| **C（推荐）** | AAP 自建小时用量表，按小时拉日志并落库                   | 不污染 new-api，字段可扩展 |

## 4. 工程风险与对策

| 风险                        | 等级 | 对策                              |
| ------------------------- | -- | ------------------------------- |
| SSRF：检测引擎主动请求供应商 URL 探测内网 | 高  | 出口走专用代理，禁内网网段/环回/元数据，白名单协议      |
| Key 泄露                    | 高  | 落库加密，日志脱敏，展示仅前 4 后 4，访问审计       |
| 检测被滥用（压测他人端点）             | 中  | 限流 + 验证端点归属                     |
| RPM/TPM 压测打爆上游            | 中  | 压测档位可配、上限保护                     |
| 编译错误导致计费错                 | 高  | 编译产物必须经模拟求值验证 + 人工确认后才写 new-api |
| new-api 升级导致 API 变更       | 中  | 集成层适配器隔离，固定已验证版本                |
| 短信成本                      | 低  | 通知合并、失败重试上限                     |

## 5. 技术栈可行性

| 层        | 选型                            |
| -------- | ----------------------------- |
| 语言/框架    | Java + Spring Boot（延续既有治理）    |
| 版本治理     | import hioas-bom              |
| 复用       | hioas-sms（短信）、AuthSphere（认证）  |
| DB       | PostgreSQL                    |
| 定时任务     | Spring Scheduling / XXL-Job   |
| 前端（供应商端） | 小程序 + H5 自适应（uni-app 或 Taro）  |
| 前端（管理端）  | Vue3 + Element Plus / ECharts |

**复杂度量级估算**（非承诺）：合计 70–114 人日，约 3.5–6 人月；建议 3 人并行 → 6–10 周。不确定性最大的是指纹模块。

## 6. 结论与建议

**Go**，按以下方式落地：

* M0（2 周）：打通"提交凭证 → 检测（TTFT/一致性/RPM/缓存四项）→ 报告"，不含指纹。
* M1（3 周）：报价单 + 编译器（含校验）+ 同步 new-api（先"生成待确认"模式）。
* M2（3 周）：合同（线下）+ 打款状态 + 小时用量统计。
* M3（持续）：指纹与真实源进阶探测（先做人工辅助版）。

**红线**：编译器产物未经模拟求值验证，禁止写入 new-api 生产环境。
