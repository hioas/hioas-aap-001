# 需求澄清 One-Pager — hioas-aap

## 5W1H

| 维度            | 内容                                                                                       |
| ------------- | ---------------------------------------------------------------------------------------- |
| **What**      | 一套"供应商自动化进件"系统：供应商自助注册提交测试凭证 → 系统多维检测验真 → 在线报价 → 电子合同 → 自动同步上架 new-api → 小时级用量核算         |
| **Why**       | 当前接入一家模型供应商需人工完成 6 个环节（拉群/收 Key/抽测/Excel 报价/手工配 new-api/事后对数），信息散落、无法验真、易配错、无审计、无法按供应商对账 |
| **Who（供给）**   | 模型供应商商务（原厂 / 渠道商 / 中转商）                                                                  |
| **Who（需求）**   | 转售运营方的商务 + 技术运营                                                                          |
| **When**      | 供应商从"有意向"到"可调用"的全周期；上架后持续小时级用量核算                                                         |
| **Where**     | 供应商侧：小程序 + H5 自适应；运营侧：管理端 Web                                                            |
| **How（技术主干）** | 检测引擎（多探测维度）+ 报价编译器（业务报价 → new-api billingexpr）+ 流程编排（状态机 + 定时任务）+ 与 new-api 管理 API 集成    |

## 目标用户与场景

### 用户 A：供应商商务（主用户）

* **画像**：手上有一批模型 API 资源（自建集群 / 上游代理），想卖给你的转售平台。熟悉价格但不懂技术细节。
* **场景**：微信收到商务邀请 → 扫码/链接进入小程序 → 手机号注册 → 提交测试端点与 Key → 等检测结果 → 收到短信通知"检测通过" → 登录填报价单 → 签合同 → 开始供货。
* **诉求**：流程快、报价灵活（不同时段不同价、阶梯价）、结果透明（知道为什么没过）。

### 用户 B：运营商务（内部）

* **画像**：负责供应商引入与价格谈判。
* **场景**：管理端看板 → 审检测报告 → 审报价单 → 一键发起合同 → 打款 → 一键上架。
* **诉求**：一屏掌握状态、减少手工配 new-api、可追溯历史报价。

### 用户 C：技术运营（内部）

* **画像**：负责网关稳定与成本。
* **场景**：配置检测项与报告模板、监控检测任务、查看用量与成本。
* **诉求**：检测项可配、报告可定制、用量可视。

## 核心价值假设（待验证）

| #  | 假设                         | 验证方式                | 风险                     |
| -- | -------------------------- | ------------------- | ---------------------- |
| H1 | 供应商愿意自助填表（而不坚持微信谈）         | M0 后观察自助完成率         | 中：老供应商习惯微信             |
| H2 | 多维指纹检测能有效识别"套壳/降级"供应商      | 人工复核 + 已知样本回归       | ：指纹是概率推断，非证明           |
| H3 | 业务报价 100% 可编译为 billingexpr | 编译覆盖测试              | 低：new-api 能力已确认（F2–F4） |
| H4 | 自动上架能替代人工配 new-api         | 灰度：先"生成配置待人工确认"再全自动 | 低                      |
| H5 | 小时级用量核算能满足供应商结算            | 与手工对账比对             | 中：缓存量缺口（F8）            |

## 核心价值主张（对外一句话）

> **"把模型接入从三天的人工杂活，变成三十分钟的自助流水线——而且它是真的。"**

## 范围界定

### In Scope（本期）

* 供应商注册/登录（手机号 + 微信授权手机号）
* 测试凭证提交（端点 URL / apikey / 模型清单）
* 检测引擎：TTFT、P50、一致性、RPM、TPM、缓存命中、模型指纹、真实源
* 检测报告生成（可配检测项 + 可配模板 + 每项解释）
* 短信通知 + 报价单（输入/输出/缓存/峰谷/阶梯/多模型）
* 报价单审核 → 合同发起 → 签署（线上/线下）→ 打款
* 渠道与价格自动同步 new-api
* 小时级用量统计

### Out of Scope（本期不做）

* 供应商侧资金结算/提现（走线下）
* 模型能力评测排行（benchmark 打分）
* 客户端用户体系改造（沿用 new-api）
* new-api 源码改造（明确不做，见 F 系列结论）

## 关键约束

| 约束      | 说明                                               |
| ------- | ------------------------------------------------ |
| **合规**  | 供应商 Key 属高敏感凭据，需加密存储 + 访问审计 + 脱敏展示；合同需电子签合规或线下留痕 |
| **安全**  | 检测引擎会主动请求外部端点 → 必须 SSRF 防护（出口白名单/代理），避免内网探测      |
| **技术栈** | 遵循已有治理：Java + Spring Boot，import hioas-bom 版本治理  |
| **不侵入** | 与 new-api 集成仅走管理 API，零源码改动                       |

## 待用户拍板的开放问题

* **检测引擎的判定阈值谁定？** 建议由管理端配置（TTFT/P50/一致性等各给"通过线"），技术运营可调。
* **"模型指纹"通过标准**——是"必须证明是真模型"，还是"无造假迹象 + 质量达标"即可？建议取后者并在报告中披露置信度。
* **合同方式**——线上电子签（需接第三方）还是线下上传扫描件？影响工期。
* **打款是否进系统**——本期建议只记录状态，不做资金流转。
