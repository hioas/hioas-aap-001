# 01 · 需求分析与场景穷举（AI 模型供给聚合与交易平台）

> 范围：`hioas-aap-001` 现有能力 + 本轮新增需求（进件自动化、一模型一渠道、双价格表、客户端/管理端）。
> 方法：先按**对象域**切分角色与实体，再沿**生命周期**穷举场景，最后落到能力清单与 Story/Case。

## 1. 需求本质（一句话）

**把「模型供给」当成可编排、可定价、可结算的商品来经营**：供应商把模型接入平台（进件），平台把它变成可调度、可计费、可结算的渠道（编排），再按用量与合同完成结算（变现）。

三条主线：
1. **进得来**：进件自动化（凭证 → 检测 → 定价 → 合同），尽量少人工。
2. **调得动**：一模型一渠道，模型级隔离与择优（某上游故障不拖垮全局）。
3. **算得清**：双价格表 + 用量归集 + 结算对账，平台与供应商都看得见、算得对。

## 2. 对象域（Domain）划分

| 域 | 核心对象 | 责任边界 |
|---|---|---|
| 身份域 IAM | 供应商账号、平台用户（4 角色）、API Key | 谁是谁、能做什么 |
| 供给域 Supply | 供应商、凭证、检测报告、供给单元（模型 × 供应商） | 供给从哪来、是否可信 |
| 商品域 Catalog | 厂商、模型、模型价格、渠道价格、比价视图 | 卖什么、卖多少钱 |
| 交易域 Trade | 报价单、合同、打款、结算单、对账单 | 怎么成交、怎么分钱 |
| 编排域 Orchestration | 渠道绑定、编译产物、同步任务、配置批次 | 怎么把商品挂到网关 |
| 计量域 Metering | 用量桶、用量明细、用量对账 | 用了多少、该付多少 |
| 治理域 Governance | 审计日志、告警、风控策略、配置版本 | 可追溯、可干预 |

**关键设计原则**：**每个域只有一个写入口**。例如「渠道在哪」只能由编排域回答；「这个模型卖多少钱」只能由商品域回答。跨域只读视图，不跨域写。

## 3. 角色与权限矩阵

| 角色 | 定位 | 典型权限 | 明确不能做 |
|---|---|---|---|
| `PROVIDER`（供应商） | 供给方 | 提交凭证、看检测结果、报价、签合同、看用量/结算单 | 看别家数据、改平台价、直接改渠道 |
| `BIZ_OPERATOR`（运营商务） | 成交与结算 | 审核报价、签发合同、确认打款、出账 | 看检测配置、改技术参数 |
| `TECH_OPS`（技术运营） | 接入与编排 | 检测配置、编译、上架、渠道编排、批量配置 | 定价、合同、打款 |
| `SUPER_ADMIN` | 全量 | 全部 | —（但操作留审计） |
| `CONSUMER`（客户端客户，新增） | 使用方 | 浏览模型、管 API Key、看用量账单 | 看供给成本、看供应商信息 |

## 4. 场景穷举（按生命周期 7 域 × 35 场景）

### A. 进件（Onboarding）— 供给进来
| # | 场景 | 触发 | 关键判定 |
|---|---|---|---|
| A1 | 供应商注册与资质提交 | 新供应商 | 企业资质齐全、USCC 唯一 |
| A2 | 凭证提交（多 Key / 多环境） | 供应商 | key 加密存储、指纹去重 |
| A3 | 凭证预检（连通/鉴权/限流） | 提交后 | 真实探活，非格式校验 |
| A4 | 深度检测 D1–D8（能力/质量/合规/稳定） | 预检通过 | 分级打分、置信度 |
| A5 | 检测不通过 → 整改复检 | 检测失败 | 差异对比、复检次数上限 |
| A6 | 人工放行（DET-06） | 边界情况 | 必须留理由与责任人 |
| A7 | **进件自动化分级 L0–L3**（新） | 四因子风险评分 | 只有四因子全低才允许全自动 |
| A8 | 供应商自助看进度 | 随时 | 状态可见、拒绝原因明确 |

### B. 定价与合同（Pricing & Contract）— 谈成
| # | 场景 | 触发 | 关键判定 |
|---|---|---|---|
| B1 | 创建报价单（多模型明细） | 检测通过 | 单价/阶梯价/有效期 |
| B2 | 多供应商比价 | 运营 | 同模型横向可比（含质量与稳定性） |
| B3 | 审核/议价/驳回 | 运营 | 驳回理由必填 |
| B4 | 合同签发与签署（SEAL） | 审核通过 | 双签才生效、文件留档 |
| B5 | 合同变更（补充协议） | 价格/门槛变化 | 版本化、不影响已出账周期 |
| B6 | 平台费率与结算门槛 | 合同条款 | 费率来源可追溯 |

### C. 模型与价格（Catalog）— 卖什么、卖多少
| # | 场景 | 触发 | 关键判定 |
|---|---|---|---|
| C1 | 模型目录维护（厂商/型号/上下文/能力标签） | 新模型 | 命名规范、能力标签枚举 |
| C2 | **模型价格表**（平台视角：基准价/对外价） | 定价 | 版本化、只增不改 |
| C3 | **渠道价格表**（采购视角：模型×供应商→生效价） | 合同生效 | 来源可回溯到报价单/合同 |
| C4 | 比价矩阵视图 | 随时 | 同模型多供应商横评 |
| C5 | 毛利视图 | 随时 | 对外价 − 采购价 − 平台成本 |
| C6 | 供给覆盖视图 | 随时 | 单模型仅 1 家 → 断供风险 |
| C7 | 价格漂移守护 | 定期 | 采购价/上游价异常波动告警 |

### D. 编排（Orchestration）— 挂上去
| # | 场景 | 触发 | 关键判定 |
|---|---|---|---|
| D1 | 一模型一渠道配置 | 合同生效/上架 | 渠道名确定性可反解 |
| D2 | 多 Key 挂同一渠道 | 同供应商多 Key | `multi_to_single` + 轮询/随机 |
| D3 | 批量配置 dry-run | 运营预演 | 零写入、差异清单可见 |
| D4 | 批量 apply（限速执行） | 确认差异 | ≤5 req/s、分批、退避 |
| D5 | 写后回读校验 | 每次写入 | 不一致 → MISMATCH，不写成功 |
| D6 | 单模型重试/回滚 | 单项失败 | 只影响该项，不整批重来 |
| D7 | 重配置（换 key/调价） | 变更 | 差异同步，不重建 |
| D8 | 渠道禁启用（auto_ban） | 上游故障 | 模型级隔离 |
| D9 | 长尾模型合并模式 | 模型过多 | 策略可配、可逆 |

## 6. Story 与 Case（代表性，全量见 04）

### Story 模板
> 作为 **<角色>**，我想要 **<能力>**，以便 **<价值>**。
> 验收：**<可执行判定>**

### A 域
- **S-A2** 作为供应商，我想一次提交多把 Key 并看到每把的检测结果，以便我知道哪把能用。
  - 验收：每把 Key 独立状态；`multi_to_single` 挂同一渠道；失败项可单独重提。
- **S-A7** 作为平台，我想让低风险进件全自动通过，以便减少人工审核。
  - 验收：四因子（金额/合规/技术/历史）全低 → 自动通过并留审计；任一为中/高 → 转人工。

### C 域（价格）
- **S-C2** 作为运营，我想维护模型对外价并按版本追溯，以便调价不影响历史账单。
  - 验收：调价生成新版本；历史结算单仍引用旧版本价格。
- **S-C3** 作为运营，我想看到「同一模型在不同供应商的采购价」，以便择优与议价。
  - 验收：比价矩阵按模型聚合，含质量分与稳定性，可下钻来源合同。

### D 域（编排）
- **S-D1** 作为技术运营，我想让每个模型独立成一个渠道，以便某个上游故障只影响该模型。
  - 验收：渠道名 = `AAP-{供应商短码}-{模型名}` 确定性生成；某渠道禁用不影响同供应商其它模型。
- **S-D3** 作为技术运营，我想先看差异再决定是否落盘，以便避免误改生产路由。
  - 验收：dry-run 零写入（上游请求数为 0）、差异清单含动作与原因。

### Case 示例（D3 dry-run）
| 项 | 内容 |
|---|---|
| 前置 | 供应商 P 已有模型 M 的渠道，当前 weight=10 |
| 步骤 | 1) 调 `POST /admin/config-batches` `{batch_type:UPDATE_CHANNEL, mode:DRY_RUN}` 2) 查批次详情 |
| 预期 | 批次 status=SUCCEEDED；明细 action=UPDATE，reason 含 `weight 10 → 20`；**网关请求数 0** |
| 异常 | 若无差异 → action=SKIP，reason 含「一致」；若上游不可达 → 不报错，仍产出差异清单 |

### Case 示例（F3 结算不出空单）
| 项 | 内容 |
|---|---|
| 前置 | 周期 2026-10 无任何用量 |
| 步骤 | `POST /admin/settlements`（ADM-PAY06） |
| 预期 | `409 E-1601`「该周期没有用量数据，不能出账」，**不生成 0 元单** |
| 异常 | 重复生成同周期已有单 → 返回既有单（幂等），不新增行 |

## 7. 场景到能力的覆盖缺口（Gap）

| 缺口 | 影响 | 优先级 |
|---|---|---|
| C-06 编排端到端未验证（APPLY 链路） | 「一模型一渠道」只有构件，无真跑通证据 | P0 |
| C-03 进件自动化未实现 | 进件仍需人工逐步操作 | P0 |
| C-05 双价格表仅规格 | 无法比价/毛利/覆盖分析 | P1 |
| C-10 客户端完全缺失 | 平台只有供给侧，没有需求侧 | P1 |
| C-09 漂移/覆盖守护未落地 | 断供与价格异常只能事后发现 | P2 |
