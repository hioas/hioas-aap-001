## 缺陷 1 · 检测执行器缺失

### 现象（浏览器实测，可复现）

```
GET /api/v1/detection-jobs/458716937126121472        → status = QUEUED, started_at = null
GET /api/v1/detection-jobs/458716937126121472/results → {"total": 0, "items": []}
```

两轮跑出两个不同任务号，症状一致。`POST /credentials/{id}/precheck` 会**成功建出任务**（`code=0`），
但任务**永停 QUEUED** → 分项结果恒空 → `/reports/*` 永不产出 → 站内信永不产生。

**注意这是「假绿」**：HTTP 200 + `code=0`。只断言状态码的联调会把它判成通过。
已在 `aap-client/tools/h5-chain.mjs` 第⑪步固化为**故意红**的业务结果断言。

### 根因（源码实证）

`DetectionService.recordProbeResults(jobId, scores, metricsByProbe, evidenceByProbe)` 是全仓库
**唯一的检测结果写入路径**，但**零调用方**（`grep -rn recordProbeResults src/` 只命中定义与注释）。

### 关键事实：注释表明执行器**本就被设计为外部组件**

`DetectionService` 类注释原文：

> 任务的**执行**（D1–D8 真实探测）由**引擎工作线程**负责，本服务提供 `recordProbeResults`
> 作为**引擎回调/离线回放的入口**——打分与结论判定全在 `ProbeScoring` 纯函数里，可独立复算。

所以这**可能不是缺陷而是设计边界**：引擎是独立组件，本仓库只留回调口。
`recordProbeResults` 的三个入参本身就是「执行器 ↔ 本服务」的接口契约。

### 现成的接口契约（执行器只需满足这个）

```java
@Transactional
DetectionViews.Job recordProbeResults(
    Long jobId,
    List<ProbeScoring.ProbeScore> scores,          // 每项：code/status/score/权重/note
    Map<String, Map<String, Object>> metricsByProbe, // 原始指标（落 metrics jsonb）
    Map<String, String> evidenceByProbe)            // 证据摘要（落 evidence）
```

打分**不用执行器管**，`ProbeScoring` 里已有 7 个纯函数，执行器只负责**采集原始指标**：

| 探针 | 名称 | 打分函数入参（= 执行器要采的东西） |
|---|---|---|
| D1 | TTFT | `scoreTtft(List<Integer> samplesMs)` — 首 token 耗时样本，**≥3 个**，不足判 FAILED |
| D2 | P50 延迟 | `scoreThroughput(double tps)` |
| D3 | 一致性 | `scoreDeterminism(int samples, int identical)` |
| D4 | RPM | `scoreQuota("D4", Double measured, Integer declared)` |
| D5 | TPM | `scoreQuota("D5", Double measured, Integer declared)` |
| D6 | 缓存命中 | `scoreCache(Boolean hit, boolean fieldPresent)` |
| D7 | 模型指纹 | `scoreFingerprint(Map<String, Double> subScores)` |
| D8 | 真实源 | `scoreUpstreamOrigin(String evidenceSummary)` |

总分与结论：`ProbeScoring.summarize(scores, passScore, vetoScore)`。

### 三个选项

| 选项 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A（推荐先做）** | **明确它是外部组件**，本仓库只留接口；补一份「执行器接入契约」文档 + 一个**离线回放工具**（把探针结果 JSON 喂给 `recordProbeResults`），让联调链路能端到端走通 | 小 | 真实检测仍依赖外部引擎；但联调不再卡死 |
| **B** | 本仓库补一个**最小可跑执行器**（按上表跑真实 HTTP 探测 → 调 `recordProbeResults`） | 中（8 个探针的真实探测逻辑 + 并发/超时/配额控制） | 与「引擎」职责重叠；D4/D5 配额、D7 指纹、D8 真实源都需要上游配合，未必能真实测 |
| **C** | 什么都不做 | 0 | 报告/站内信/打款链路永久断，联调只能靠 DET-06 人工放行绕过 |

**我的建议：A**。理由：注释已明确执行器是外部组件，本仓库补 B 会造出职责重叠的第二实现；
但联调需要一条能走通的路径，所以补「离线回放工具 + 契约文档」性价比最高，且**不越界**。
若你确认引擎在本仓库内，那就选 B，我按 TDD 实现（先红：任务应离开 QUEUED）。

## 缺陷 2 · 文件上传端点缺失

### 现象（curl 实测，逐条可复现）

```
POST /admin/contracts/458711028085776384/issue  {}
  → E-1001  details: [{field:"file_id", reason:"合同文件必填"}]

POST /admin/contracts/458711028085776384/issue  {"file_id":"1"}
  → E-1001  details: [{field:"file_id", reason:"合同文件不存在：1"}]
```

`POST /contracts/{id}/sign` 同样 `E-1001`；`GET /contracts/{id}/file` → `E-1701 合同尚未签发（当前：CREATED）`。

### 根因（源码实证，铁证）

`aap_file_asset` 表**在** `V1__baseline.sql:1145` 存在（对象存储导向：`file_key`/`bucket`/`sha256`/`content_type`/`size_bytes`），
但**主代码里只有 3 处 SELECT，零 INSERT**：

```
ContractService.java:80   left join aap_file_asset f on f.id = c.file_id ...
ContractService.java:169  select file_key, original_name from aap_file_asset where id = ?
ContractService.java:243  select count(*) from aap_file_asset where id = ?   ← issue 的前置校验
```

唯一的两处 INSERT 都在**测试代码**里（`ContractContractTest.java:106`、`PaymentContractTest.java:105`
手动插数据）。全后端 `MultipartFile` / 上传端点 / 对象存储客户端（oss|minio|s3）**均零命中**。

**结论**：`file_id` 在生产路径下**不可能被创建** → 合同永远停在 `CREATED`，签不了、打不了款。

**为什么测试全绿**：测试自己手动 INSERT 了那条文件记录。这是「测试全绿、真实链路断」的
典型案例，也是「联调必须走真实链路」的直接论据。

### 三个选项

| 选项 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A（推荐）** | 补 `POST /api/v1/files`（multipart）→ 写 `aap_file_asset` + 文件落**本地磁盘**，`file_key` 用相对路径；对象存储留 `StorageBackend` 接口位（默认 Local 实现）。⚠️ 需**新增配置项**（当前 `application.yml` 无任何 storage 配置，实测 grep 零命中），命名与默认值我按项目现有风格提（如 `app.storage.local-root` ← `${AAP_STORAGE_LOCAL_ROOT:./data/files}`），**待你确认** | 中（端点 + 存储抽象 + 校验：大小/类型/sha256/鉴权/审计） | 需要定：允许的 content-type、单文件大小上限、谁能传（ADMIN only 还是 SUPPLIER 也能传） |
| **B** | 同上但直接落对象存储 | 中 + 需要 OSS/S3 地址与凭据 | 本地联调没有对象存储；凭据管理要走 `E:\env` |
| **C** | 文件由管理端**线下灌入**（DBA/运维手工 INSERT），本仓库只保留读接口 | 0（不改代码） | 生产不可运维；合同流程事实上无法自助完成 |

**我的建议：A**。本地联调能立刻跑通，且 `StorageBackend` 抽象让后续换对象存储是纯替换。

**选 A 需要你定 3 件事**（不定我就按最保守的默认值实现并标 `missing-prd`）：
1. 允许的 content-type：默认 `application/pdf` + `image/*`
2. 单文件大小上限：默认 20 MB
3. 上传权限：默认 **ADMIN 与 SUPPLIER 都可传**（合同文件由管理端传、资质文件由供应商传）

## 缺陷 7 · H5 地区选择器不可用

### 现象（浏览器实测）

H5 打开 `/pages/profile-edit/index`，控制台稳定 4 条：

```
[Vue warn]: Invalid prop: custom validator check failed for prop "mode".
  at <Picker> at <View> ... at <Index>
```

### 根因（读 uni-app 源码实证）

`@dcloudio/uni-h5/dist/uni-h5.es.js:25525`：

```js
const mode = {
  SELECTOR: "selector",
  MULTISELECTOR: "multiSelector",
  TIME: "time",
  DATE: "date"
  // 暂不支持城市选择
  // REGION: 'region'        ← 被注释掉
};
// mode 的 prop 定义：
validator(val) { return Object.values(mode).includes(val); }
```

本页用 `mode="region"` → validator 失败 → **H5 上该控件不渲染**。
微信小程序支持 region，**故这是真实双端差异**。

页面注释原本写的是「地区数据源 PRD 无定义 → **用平台内置数据**」——微信有内置数据，H5 没有。
台账序号 10 备注⑫原判为「无头环境无法驱动原生控件」，**该判断有误**，已更正。

### 三个选项

| 选项 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A（推荐）** | `#ifdef MP-WEIXIN` 保持 `mode="region"` 不变；`#ifndef` 分支降级为「省 / 市」两个文本输入（同 `form.province`/`form.city` 字段、同校验） | 小 | H5 录入体验略降；但**不臆造行政区划数据**，且随时可替换 |
| **B** | H5 自绘省市级联（`mode="multiSelector"` + 内置行政区划数据） | 中（要引入 34 省 + 300+ 地级市数据） | **PRD 无该数据源** → 算新增产品数据，需你确认数据来源与版本 |
| **C** | H5 隐藏该项，明确「地区仅小程序端可编辑」 | 小 | H5 用户档案完整度永远补不齐 → 影响完整度相关链路 |

**我的建议：A**。改动最小、不引入未定义数据、两端字段语义一致；若以后要 B，只是把
`#ifndef` 分支换成级联组件，其余不动。

## 三项之间的关系（避免只修一半）

```
凭证 → 预检 → 检测任务（缺陷1：永停 QUEUED）→ 报告 → 报价 → 审核 → 合同（缺陷2：签不了）
                     ↑ 卡死在这里                                    ↑ 卡死在这里
档案完整度 ← 地区字段（缺陷7：H5 填不了）
```

- 缺陷 1 不修：**报告、站内信、以及依赖报告的报价审核全部不可达**（联调只能靠 DET-06 人工放行绕过）
- 缺陷 2 不修：**合同流程从签发起断**，打款链路跟着断
- 缺陷 7 不修：只影响 H5 的档案完整度，**不阻塞主链路**

优先级建议：**缺陷1（选 A 补离线回放 + 契约）> 缺陷2（选 A 补上传端点）> 缺陷7（选 A 降级文本）**。
