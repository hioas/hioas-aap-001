# 00 · 现状梳理（现有资产 → SDD 映射）

> 目的：把项目**已有**的设计与实现资产盘清楚，再决定哪些进 SDD 的哪一份文档。
> 结论先行：**本项目不缺设计，缺的是 SDD 的组织方式** —— 已有 22 份 PRD 覆盖了 spec/plan/tasks 的
> 全部内容，但它们按「PRD 分册」组织，不按「规格 → 计划 → 任务 → 契约」组织，导致三件事说不清：
> ① 每份文档的**读者与约束力**（哪些是红线、哪些是建议）；② 需求到代码的**追踪链**；
> ③ 变更时**该改哪一份**。本次重组围绕这三点。

### 1.3 既有工程纪律（必须继承，写进 constitution）

1. **new-api 零源码改动** —— 全部通过其管理 API 集成（`03-new-api_能力基线.md` §3）。
2. **编译红线** —— 未经模拟求值校验的表达式禁止写入生产（`11-同步与用量统计PRD.md` 红线）。
3. **凭证安全** —— AES-256-GCM 密文 `base64(iv||ct||tag)`；明文仅超管 + 二次验证 + 审计；
   日志/异常栈/指标不得含明文。
4. **提交卫生** —— 多会话共用仓库，`git add` 必须逐路径显式列出，他方在制品只登记不碰。
5. **证据可追溯** —— 结论必须给出「文件:行号」；跑批读数落 `.agents/state/evidence/`。

## 3. 现状与新需求的差距（本次要解决的）

### 3.1 范式差距：渠道粒度

| | 现有设计 | 本次需求 |
| --- | --- | --- |
| 渠道单元 | **一个供应商 = 一条渠道**（`channel_name = AAP-{short_code}-{seq}`，`models` 为逗号分隔列表） | **一个模型 = 一条渠道**（渠道名 = 模型名 + 渠道名） |
| 证据 | `11-同步与用量统计PRD.md` §3「渠道字段映射」；`15-` §4 `aap_channel_binding`：`channel_name` 唯一、`models` 多值 | 用户 2026-09-25 指示 |

**这不是命名调整，而是可调度单元的重新定义**（详见 `specs/001-intake-automation/spec.md` §3）：
渠道粒度决定 new-api 侧**故障隔离、负载分流、启停、限速、参数覆盖**的作用范围。
粒度从「供应商」细化到「模型」后，上述能力全部从供应商级提升为**模型级**，代价是渠道数从 M 变为 M×N。

### 3.2 视图差距：缺两张价格表

现有有报价单（`aap_quote_item`，供应商侧输入）与编译产物（`aap_model_expression`，写入侧），
但有**两个视角空着**：

- **模型价格表**：平台视角的模型目录 + 基准价/参考价（`aap_reference_price` 表存在，但没有对外视图与维护流程）。
- **渠道价格表**：`（渠道 × 模型）→ 生效价` 的矩阵 —— 对账基准、比价矩阵、改价审计的共同载体。**完全缺失**。

### 3.3 自动化差距：进件仍是分段人工

现有设计有闸门③人工确认 + 灰度三阶段（`11-` §3），自动化程度 L1（半自动）。
本次要求「进件自动化」= 端到端流水线，需要**自动化分级**与**风险矩阵**（不能一刀切全自动）。

## 4. 本次重组策略

1. **不推翻既有一行设计** —— 22 份 PRD 是需求真源，本次只做**组织方式重构 + 增量设计**。
2. **新建 `.specify/` 与 `specs/`** —— 与既有 `.calicat/prd/` 并存，前者是「执行规格」，后者是「需求册」。
   映射关系写进 `specs/001-intake-automation/spec.md` 的「来源」列。
3. **契约服从生成器** —— `contracts/` 只登记「本次新增端点的规格」，最终以 `gen-backend-models.py` 生成物为准。
4. **每条结论可追溯** —— 引用「文件 §/行」或官方文档 URL。
5. **未决项显式标记** —— 用 `[NEEDS CLARIFICATION]`，不假装已定。
