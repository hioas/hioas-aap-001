## 1. 背景与问题

平台把 AI 模型供应商接入到可调度、可计费、可结算的状态，当前需要五个角色反复人工搬运：

1. 供应商提交凭证后，运营手工判断「这家的模型能不能用」；
2. 检测通过后，供应商与运营在聊天工具里来回谈价，价格靠人工填表；
3. 合同与打款全靠线下；
4. 上架时运营手工在 new-api 里建渠道、勾模型、填 base_url 与 key；
5. 上架后价格与用量无人对照，供应商实际质量与承诺脱节。

**问题本质**：进件是一条**有状态、有闸门、有多方参与的长流水线**，但每一步的工具是断开的——
状态靠人记、凭证靠人传、价格靠人抄、渠道靠人建。断点越多，漏项与错配越多。

**本次要解决的三件事**：

- **P1 自动化**：把「凭证 → 上架」串成一条可观测、可断点续跑、可分级的流水线；
- **P2 渠道粒度**：把可调度单元从「一个供应商」细化到「一个模型」；
- **P3 价格可见**：补上「模型价格表」与「渠道价格表」两个一直缺失的视角。

## 2. 目标与成功度量

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| **北极星** | 供应商从提交凭证到上架的中位时长 | ≤ **3 天**（其中系统侧 ≤ **2 小时**） |
| 自动化率 | 全自动（L2/L3）完成的进件占比 | ≥ **60%**（低风险档首发） |
| 配置正确率 | 渠道写入后回读校验一致的比例 | **100%**（不一致必须告警，不得静默成功） |
| 价格偏差率 | 实际结算单价 vs 渠道价格表生效价的偏差 | **|偏差| ≤ 5%**（超阈值告警） |
| 复测降级率 | 上架后 30 天内被判定「疑似降级」的比例 | < **2%** |
| 人工介入率 | 需要运营人工处理才能推进的进件占比 | ≤ **30%** |

## 3. 术语与核心概念

### 3.1 术语

| 术语 | 定义 |
| --- | --- |
| 进件（Intake） | 一个供应商的一次完整接入过程：凭证 → 检测 → 报价 → 合同 → 打款 → 配置 → 上架 |
| 凭证（Credential） | `base_url + api_key + 声明模型清单` 三要素，是上游能力的唯一入口 |
| 检测（Detection） | D1–D8 八项探测，产出分项得分与可解释报告 |
| 报价（Quote） | 供应商对每个模型的报价单（八大单价 + 时段/阶梯/请求级规则） |
| 编译（Compilation） | 报价 → 计费表达式（真实单价，带 `v1:` 前缀）的确定性转换 |
| **渠道（Channel）** | new-api 侧的最小可调度单元：一条上游地址 + 一份凭证 + 一组模型 + 调度参数 |
| **供给单元（Supply Unit）** | 本特性引入：`模型 × 供应商` 的最小组合，与一条渠道一一对应 |
| 模型价格表 | 平台视角：模型目录 + 平台基准价/对外价 |
| 渠道价格表 | 采购视角：`(渠道 × 模型) → 生效价` 的矩阵，对账基准 |

### 3.2 核心范式：可调度单元 = 模型 × 供应商 ★

**现有做法**：一个供应商一条渠道，`models` 字段是逗号分隔的模型清单。
**本特性做法**：**一个模型一条渠道**，渠道名 = `供应商短码 + 模型名`。

**为什么改**（这是本 spec 的立论，请评审重点看）：

new-api 的调度能力全部挂在**渠道**上：`priority`（优先级）、`weight`（同优先级随机权重）、
`auto_ban`（连续失败自动禁用）、`status`（启停）、`param_override`/`header_override`（参数与请求头覆盖）、
以及按渠道的限流与用量归集。

| 能力 | 渠道=供应商时的作用范围 | 渠道=模型×供应商时的作用范围 |
| --- | --- | --- |
| 故障自动禁用 | 一个模型炸了 → **整个供应商下线** | 只有该模型下线，同供应商其他模型不受影响 |
| 负载分流/择优 | 只能在**供应商层级**选，同供应商内模型无法分开调度 | 同一模型可对接多个供应商并按 `priority/weight` **分流择优** |
| 启停 | 停供应商 = 停全部模型 | 可按模型灰度停用 |
| 参数覆盖 | 全供应商一套 | 不同模型不同策略（采样、超时、推理档位） |
| 用量归集 | `(渠道, 模型)` 是多对多，需拆解 | `(渠道, 模型)` **天然 1:1**，对账与结算直接可用 |

**代价**（必须一起看）：

| 代价 | 程度 | 缓解 |
| --- | --- | --- |
| 渠道数从 M 变为 M×N | 高（100 供应商 × 20 模型 = 2000 渠道） | 批量创建 + 按供应商打 `tag` 组织；长尾模型走合并模式（见 DR-03）；渠道数阈值压测（research T-5） |
| 同一 key 在 N 条渠道中重复 | 中（泄露面 ×N、轮换成本 ×N） | 改用 new-api 多 Key 模式；key 密文集中管理；轮换走集中批量更新（DR-06） |
| 建渠道请求数 ×N | 低 | 原生批量模式（`mode: batch`，research §2.1） |
| 渠道命名空间冲突 | 低 | 命名规则确定性生成 + 唯一性校验（§3.3） |

### 3.3 渠道命名规则

```
channel_name = "AAP-" + short_code + "-" + model_slug
model_slug   = 模型名中的非法字符（/ : 空格 等）归一为 "_"，超长截断并附 4 位哈希
```

- **可反解**：从渠道名可解析出供应商与模型，便于运维对账与故障定位。
- **确定性**：同供应商同模型重复配置 → 生成同名 → 天然幂等（配合幂等键）。
- **例外**：合并模式下沿用旧规则 `AAP-{short_code}-{seq}`，且**不得与模型级渠道同名**。

### 3.4 自动化分级（L0–L3）

| 等级 | 行为 | 适用 |
| --- | --- | --- |
| **L0 全人工** | 系统只记录，不推进 | 申诉/异常件 |
| **L1 半自动**（默认） | 系统生成草稿（报价单/合同/渠道配置），**人工确认后执行** | 新供应商、高风险档 |
| **L2 自动（带复核）** | 自动执行，但**抽样复核 + 强审计** | 白名单供应商、低风险模型 |
| **L3 全自动** | 无人工介入，异常才转人工 | 已复测通过的老供应商 + 标准模型 |

**分级依据（风险矩阵）**：

| 因子 | 低风险 | 中风险 | 高风险 |
| --- | --- | --- | --- |
| 供应商类型 | 一手原厂（ORIGINAL） | 转售（RESELLER） | 聚合（AGGREGATOR） |
| 检测结果 | PASS 且指纹置信度 HIGH | PASS 中置信度 | MANUAL_REVIEW / 指纹置信度 LOW |
| 模型风险 | 标准模型（平台目录内） | 目录外新模型 | 高价值模型（单价 > 阈值） |
| 金额 | < 阈值 A | 阈值 A–B | > 阈值 B |

规则：四个因子**全部低风险** → 允许 L3；其中任一为中风险 → 最高 L2；出现高风险 → L1；
**红线 C-02（编译闸门②）在任何等级都不得跳过**。

## 4. 功能需求

### FR-1 进件流水线（自动化编排）

| 编号 | 需求 |
| --- | --- |
| FR-1.1 | 供应商提交凭证后，系统自动完成预检（地址合法性/连通性/模型清单核对）并给出可读结论 |
| FR-1.2 | 预检通过自动排队检测；检测完成自动产出报告并触发下一阶段判定（无需人工点「下一步」） |
| FR-1.3 | 检测通过后，系统**自动生成报价单草稿**（含模型清单与建议价）；建议价来源优先级：供应商已提交报价 > 上游倍率同步 > 平台参考价 |
| FR-1.4 | 报价单按 D-… 校验规则校验，非法区间必须定位到具体字段（模型/规则/档位） |
| FR-1.5 | 报价单通过审核后自动推进到合同；合同支持模板化生成 + 线下盖章件回传 + 状态推进 |
| FR-1.6 | 打款确认后自动触发上架配置（FR-2），无需运营在 new-api 手工建渠道 |
| FR-1.7 | 流水线全程可观测：当前阶段、已完成阶段、卡点原因、预计剩余步骤 |
| FR-1.8 | 任一步骤失败必须**可断点续跑**（从失败步骤重试，不重跑已完成步骤） |
| FR-1.9 | 每步的执行必须留痕：执行人（人或系统）、时间、输入摘要、结果、失败原因 |
| FR-1.10 | 系统按 §3.4 风险矩阵为每个进件**计算自动化等级**，等级变更需记录原因 |

### FR-2 渠道自动配置（本特性的技术核心）

| 编号 | 需求 |
| --- | --- |
| FR-2.1 | 对每个「模型 × 供应商」供给单元，自动创建一条渠道，命名遵循 §3.3 |
| FR-2.2 | 渠道的 `models` 字段**只含该模型**（一模型一渠道的直接体现） |
| FR-2.3 | 渠道的 `base_url`/`key` 来自凭证（解密后写入，日志必须脱敏） |
| FR-2.4 | 调度参数按策略填充：`priority`（供应商等级越高越优先）、`weight`（按检测分数与质量反馈加权）、`auto_ban`（开启）、`tag`（= 供应商短码） |
| FR-2.5 | 渠道创建采用**批量模式**，支持部分失败：成功的保留，失败的按单模型独立回滚/重试 |
| FR-2.6 | 每次写入遵循「**读前对比 → 写入 → 写后回读**」；回读不一致必须告警并进入重试，**不得静默成功** |
| FR-2.7 | 渠道创建必须幂等：重复执行同一进件的配置步骤，渠道数不得增加 |
| FR-2.8 | 定价写入：编译产物按模型写入生效价；**红线 C-02 闸门未过禁止写入** |
| FR-2.9 | 支持「重配置」：凭证/价格/调度策略变化后，一键重算并同步差异（只改动变化的渠道） |
| FR-2.10 | 支持「下线」：把某模型（或某供应商全部模型）的渠道置为禁用/删除，并留痕 |
| FR-2.11 | 支持**合并模式**（`channel_granularity = PER_PROVIDER`），用于长尾模型；模式可配置且转换需显式确认 |

### FR-3 模型价格表（平台视角）

| 编号 | 需求 |
| --- | --- |
| FR-3.1 | 维护平台模型目录：模型名、厂商、能力标签（文本/多模态/工具调用）、上下文窗口、状态（在架/停用） |
| FR-3.2 | 维护每个模型的**基准价**（输入/输出/缓存读写）与**对外价**，支持生效时间与版本 |
| FR-3.3 | 支持从网关侧同步模型清单与定价（来源可为上游倍率或网关定价配置），同步结果需**人工可复核** |
| FR-3.4 | 支持批量调价（按厂商/按标签/按比例），调价前给出影响面预览（涉及多少渠道/供应商/预估影响金额） |
| FR-3.5 | 展示每个模型的**供给覆盖**：有哪些供应商在供、各自价格、各自质量分 —— 支撑「这个模型谁最划算」 |
| FR-3.6 | 模型停用时，必须提示受影响的渠道数与在跑用量，禁止无声停用 |

### FR-4 渠道价格表（采购视角）

| 编号 | 需求 |
| --- | --- |
| FR-4.1 | 以矩阵形式展示 `(模型 × 供应商) → 生效价`，支持按模型/供应商/价差/质量排序筛选 |
| FR-4.2 | 每条记录展示：生效单价（分项）、来源报价单与版本、编译产物版本、生效时间、同步状态、最近回读结果 |
| FR-4.3 | 展示**价差视图**：同一模型不同供应商的价格对比，以及相对平台基准价的溢价/折价 |
| FR-4.4 | 展示**毛利视图**：渠道价（采购成本）与模型对外价之差，按模型/供应商聚合 |
| FR-4.5 | 价格变更留痕：谁在何时把哪个模型的价从多少改到多少，依据哪份报价单/合同 |
| FR-4.6 | 与用量数据对齐：渠道价格表的生效价 × 实际用量 = 应计金额，与结算单口径一致 |

### FR-5 供应商端功能

| 编号 | 需求 |
| --- | --- |
| FR-5.1 | 进件向导：一屏呈现流水线当前状态与下一步动作，可点击直接进入 |
| FR-5.2 | 凭证管理：提交、查看（脱敏）、更新、设为失效；更新后提示将触发的重配置 |
| FR-5.3 | 检测进度与报告：分项得分、可解释说明、复测入口 |
| FR-5.4 | 报价：按模型填价（八大单价 + 时段/阶梯规则），提交前本地校验并给出问题定位 |
| FR-5.5 | 「我的模型」：我供应的模型、在各渠道的生效状态、被调用的质量反馈摘要 |
| FR-5.6 | 用量与对账：按模型/小时查看用量与按渠道价格表计算的应计金额，可导出 |
| FR-5.7 | 结算单：周期、金额构成、平台费、确认状态，可查看明细 |
| FR-5.8 | 通知：进件各阶段结果、异常、复测提醒 |

### FR-6 管理端功能

| 编号 | 需求 |
| --- | --- |
| FR-6.1 | 进件漏斗看板：各阶段数量、平均停留时长、卡点 TOP N、自动化等级分布 |
| FR-6.2 | 自动配置控制台：批量建渠道任务的进度、成功/失败/回读不一致清单、按单模型重试与回滚 |
| FR-6.3 | **预演（dry-run）**：对一批供给单元预演将创建/变更的渠道与价格，产出差异清单，不写生产 |
| FR-6.4 | 调度编排：按模型配置多供应商的 priority/weight 策略，支持按检测分数与质量反馈自动调权 |
| FR-6.5 | 批量操作：按供应商/模型/标签批量启用、禁用、改价、重配；操作前给出影响面确认 |
| FR-6.6 | 模型价格表与渠道价格表管理（见 FR-3/FR-4） |
| FR-6.7 | 价格漂移看板：实际结算价与生效价偏差超阈值的供给单元清单与处理入口 |
| FR-6.8 | 审计检索：按进件/供应商/模型检索全部配置动作与结果 |

### FR-7 治理与守护（持续性）

| 编号 | 需求 |
| --- | --- |
| FR-7.1 | **质量反馈调度**：检测分数、上线后实测（成功率/时延/报错率）作为渠道 `weight` 的输入，定期重算 |
| FR-7.2 | **价格漂移守护**：定期对比上游实际价与生效价，偏差超阈值告警，可配置「自动停用该渠道」 |
| FR-7.3 | **复测与降级**：按供应商复测周期自动安排复测；判定降级时按规则降权/告警/停用，并通知供应商 |
| FR-7.4 | **供给覆盖守护**：某模型可用供应商数低于阈值时告警（单点风险） |
| FR-7.5 | 所有治理动作必须可解释：为什么降权、依据哪次检测/哪个指标 |

## 5. 创新点（相对现有设计的增量）

| 编号 | 创新 | 价值 |
| --- | --- | --- |
| **INNOV-1** | **可调度单元 = 模型 × 供应商** | 把网关的渠道级调度能力（权重/熔断/参数覆盖）提升到模型级；同一模型多供应商可自动分流择优；故障隔离从供应商级细化到模型级 |
| **INNOV-2** | **双价格表 + 毛利视图** | 平台基准价与采购成本分离，第一次能回答「这个模型我赚多少、该不该换供应商、该不该调价」 |
| **INNOV-3** | **自动化分级 + 风险矩阵** | 自动化不是开关而是分级；高风险件保人工、低风险件全自动，兼顾速度与安全 |
| **INNOV-4** | **检测结果 → 路由权重闭环** | 检测（D1–D8）与上线后实测不再是「存档的报告」，而是直接驱动渠道权重，质量差自动降权 |
| **INNOV-5** | **价格漂移守护** | 从上游同步实际价并持续对比生效价，把「价格悄悄变了没人知道」变成可控风险 |
| **INNOV-6** | **供给覆盖守护** | 某模型只剩一个供应商时告警，避免单点断供 |
| **INNOV-7** | **重配置（凭证/策略变更后一键同步差异）** | 供应商换 key、调价、改调度策略不再需要人工重来一遍 |

## 6. 业务规则增量（R-xx）

> 与既有 53 条规则（`17-零歧义执行规格spec.md` §5）并存，编号续接。

| 编号 | 规则 |
| --- | --- |
| R-54 | 渠道命名必须由 `short_code + model_slug` 确定性生成；同名冲突视为同一供给单元（幂等），不得创建第二条 |
| R-55 | `model_slug` 转换后长度超限时截断并追加 4 位哈希，保证可反解与唯一 |
| R-56 | 一条渠道的 `models` 字段必须恰好等于一个模型（PER_MODEL 模式下）；多值即为违规，配置校验必须拒绝 |
| R-57 | 批量写入必须限速且分批（默认 ≤5 req/s、每批 ≤20），失败退避 30s/2m/10m，禁止无退避重试 |
| R-58 | 任何渠道写入后必须回读；回读不一致 → 告警 + 重试；重试耗尽 → 转人工，且该供给单元标记为「配置未收敛」 |
| R-59 | 单模型失败只回滚该模型对应的渠道与定价，不得波及其他模型 |
| R-60 | 自动化等级由风险矩阵计算；等级提升（更自动）必须有依据记录；降级可自动触发但必须通知 |
| R-61 | L3 全自动禁止用于：首次接入该供应商、指纹置信度 LOW、单价超阈值、合并模式转换 |
| R-62 | 渠道价格表的生效价必须以编译产物为唯一来源；禁止手工直接改价（人工改价必须先改报价单再编译） |
| R-63 | 价格漂移超阈值（默认 ±5%）必须告警；连续两个周期漂移未处理 → 自动降权 |
| R-64 | 治理类自动动作（降权/停用）必须先告警后执行，执行后在进件与供应商页面可见原因 |
| R-65 | 模型停用/渠道下线前必须校验影响面（在跑用量、关联结算周期），有未结清账期时禁止操作 |

## 7. 验收标准（可执行、可判定）

| 编号 | 场景 | 判定 |
| --- | --- | --- |
| **AC-01** | 供应商提交含 3 个模型的凭证，检测通过，合同与打款完成 | 系统在无人工介入下创建 **3 条**渠道，`models` 各为单模型，命名符合 §3.3 |
| **AC-02** | 对 AC-01 的 3 条渠道做回读校验 | 3/3 一致（名称、base_url、models、status、调度参数），且校验结论落库 |
| **AC-03** | 重复执行 AC-01 的配置步骤 | 渠道总数不变（幂等），不产生重复渠道；日志显示「已存在，跳过/更新」 |
| **AC-04** | 3 个模型中 1 个的渠道写入失败 | 仅该模型回滚，另 2 条保持正常；失败模型标记「配置未收敛」并可单独重试 |
| **AC-05** | 某模型的上游持续报错 | 该渠道被自动禁用（`auto_ban`），**同供应商其他模型渠道不受影响** |
| **AC-06** | 同一模型接入 2 个供应商 | 两条渠道并存；按 `priority/weight` 分流，可观测到流量分配比例 |
| **AC-07** | 供应商更新凭证（换 key） | 触发重配置，仅相关渠道的 key 被更新；旧渠道不重建；留痕含变更前后对比（脱敏） |
| **AC-08** | 供应商调价（某模型输入价 +10%） | 报价单 → 编译 → 写入 → 回读全通；渠道价格表展示新价与来源版本；旧价进入历史 |
| **AC-09** | 未通过编译闸门②的报价 | 拒绝写入生产定价，错误定位到具体规则/字段；渠道价格表不出现该价 |
| **AC-10** | 管理端对 20 个供给单元执行 dry-run | 输出将创建/变更的差异清单，**生产零写入** |
| **AC-11** | 批量创建 100 条渠道 | 全流程限速（≤5 req/s）执行；失败重试带退避；无 API 过载错误 |
| **AC-12** | 模型价格表批量调价 +10% | 调价前展示影响面（渠道数/供应商数/预估金额），确认后生效，可回滚 |
| **AC-13** | 渠道价格表查看某模型 | 展示全部供应商的生效价排序 + 相对平台基准价的溢价/折价 + 毛利 |
| **AC-14** | 上游实际价与生效价偏差 8%（阈值 5%） | 价格漂移看板告警；连续两周期未处理则自动降权并可解释 |
| **AC-15** | 某模型可用供应商数降到 1 | 供给覆盖告警触发 |
| **AC-16** | 复测判定降级 | 渠道权重下调、供应商收到通知、管理端可见原因 |
| **AC-17** | 高风险件（AGGREGATOR + 指纹 LOW） | 自动化等级为 L1，必须人工确认后才能写生产 |
| **AC-18** | 任意一次渠道写入 | 日志与审计中**零明文凭证**（对 base_url/key/bearer 全字段扫描） |
| **AC-19** | 供应商端查看自己 3 个模型的生效状态与用量 | 只读可见，且只含自己的数据（越权访问返回与「不存在」相同的结果） |
| **AC-20** | 用合并模式配置一个长尾模型集合 | 生成 1 条合并渠道（旧命名规则），模型清单多值；**不与任何模型级渠道同名** |

## 8. 非功能需求

| 维度 | 要求 |
| --- | --- |
| 性能 | 管理端列表 P95 < 500ms；批量配置单批（20 条）写入 + 回读 < 60s；进件看板 P95 < 1s |
| 一致性 | 渠道与定价写入最终一致；不一致必须可见（配置未收敛清单），不得默默吞掉 |
| 可用性 | 网关侧不可用时：进件不阻塞（进重试队列），报价与检测照常；降级到人工路径必须可行 |
| 可观测 | 每步有结构化日志与指标；关键指标：配置成功率、回读不一致数、重试耗尽数、漂移告警数、自动化率 |
| 安全 | 凭证零明文（C-03）；批量操作需二次确认（影响面 > 阈值时）；治理类操作全程审计 |
| 合规 | 措辞不宣称「保证为真」；不承诺上游质量；模型停用需告知供应商 |
